# AutoResearch v2.1: planner prompt fix (anchored aspects, 1-5 aspects, few-shot examples)

v2.1 changes **only the planner prompt** (and `PLANNER_VERSION`). Retrieval and merging are
exactly as in v2. It targets the v2 failure mode where **aspects lost the question's core
requirement**: on q5 an aspect drifted into generic RLHF papers instead of *domain-specific
agents*, and on q11 splitting by approach lost the *comparison*.

**Headline (11 questions, macro-average):** v2.1 is the best system at the top of the list:
P@10 **0.936** (v2: 0.909, v1: 0.927) and nDCG@10 **0.914** (v2: 0.892), with recall unchanged
(R@50 0.470 vs. 0.472). q5 goes from the worst system to the best (R@50 0.305 → 0.375).

## What changed

### 1. Prompt rules (`autoresearch/planner.py`, `PLANNER_INSTRUCTIONS`)
| Rule | v2 | v2.1 |
|---|---|---|
| Number of aspects | 2-5 | **1-5**: a focused question gets exactly 1; only split when the question has genuinely separate parts |
| Anchoring | none | identify the question's **core subject** first; every aspect must be about it ("X for Y, never X in general") |
| Comparison questions | none | one aspect per approach, each tied to the core subject, **plus one aspect for direct comparisons** |
| BM25 keywords | exact terms, synonyms, acronyms | same, and **must include the core subject's terms**; more near-universal words to avoid (performance, results, evaluation) |

### 2. Few-shot examples
Three worked examples with full output (name, description, BM25 query, HyDE abstract):

| Example question | Teaches |
|---|---|
| How do tokenizers affect the performance of multilingual language models? | a focused question gets **1 aspect** |
| How is chain-of-thought prompting used to improve code generation, and how is it evaluated? | **2 aspects, both anchored** to "CoT for code generation", not "CoT in general" |
| Should instruction tuning or in-context learning be used for low-resource NER? | **one aspect per approach + a comparison aspect**, all anchored to low-resource NER |

**None of the examples is an eval question.** Using eval questions as examples would tune the
planner to the test set (leakage) and inflate every reported number. A code comment records this,
and the prompt was checked against `eval/queries.jsonl`.

### 3. `PLANNER_VERSION = "v2"`
Plans are cached by (question, planner model, `PLANNER_VERSION`). Changing the prompt alone would
keep returning the cached v1 plans, so the version bump forces fresh plans. Old plans stay in the
cache, so v2 remains reproducible, and every run records the planner version in `run_meta.json`.

### 4. Guard
If the planner returns zero aspects, the system raises an error instead of returning nothing.
1-aspect plans were tested end to end (RRF across a single aspect list = that list).

### Cost
- Planner: 11 calls, 22,108 input + 6,781 output tokens, **$0.009 total** (the prompt grew to
  ~1,300 words; the shared prefix now qualifies for OpenAI prompt caching).
- Judging the new run: 107 new calls, $0.033.

## Observations

- **q5 fixed.** One anchored aspect, *"Post-training methods for domain-specific agents"*,
  replaces v2's four aspects (one of which drifted into generic RLHF). R@50 0.305 → 0.375 and
  own-run P@50 0.78 → 0.96: from the worst of the five systems on q5 to the best.
- **q11 fixed.** The plan now includes a comparison aspect, *"Choosing context strategies"*.
  Aspects agree far more (46 of 50 final papers retrieved by 2+ aspects, up from 28); P@10
  0.8 → 1.0, nDCG@50 0.857 → 0.897.
- **q4 partly fixed.** HALoGEN (rank 29) and the alignment trade-off paper (rank 38) return to
  the top 50; HalluLens does not, and v1 hybrid still ranks all four higher (2, 3, 9, 13). q4's
  aspects remain causes / training data / mitigation; the missing papers are hallucination
  *benchmarks*, which the question does not ask about directly.
- **Fewer aspects means less breadth on some multi-part questions.** q7 (4 → 2 aspects; dropped
  *private information leakage* and *privacy-utility evaluation*) R@50 0.542 → 0.482; q10
  (4 → 1) 0.456 → 0.427; q6 (3 → 2) 0.483 → 0.448. Aggregate recall is unchanged because these
  are offset by q5, q9 and q11.
- **Generic keywords persist.** Despite the rule, the planner keeps writing `LLM large language
  model` into BM25 queries; q4's three aspects each match 17,600+ of 17,933 papers. Prompt
  instructions alone don't fix this; a deterministic filter in code would.

## Decision

Accepted as the new system version: better at the top (P@10, nDCG@10, nDCG@50), equal recall,
two clear fixes (q5, q11). The breadth regressions (q7, q10, q6) are **not** tuned away with more
prompt edits, which would start to overfit the 11 eval questions. They are the target of the
agent loop, which checks per-aspect coverage and expands weak aspects.

## Next

- **Verifier**: the system's own LLM check that reads retrieved abstracts and filters/reranks
  (separate prompt from the eval judge).
- **Agent loop**: after verification, check how well each aspect is covered; expand weak aspects
  with new queries, up to 3 rounds.
- **Generic-term filter** for BM25 queries (deterministic, in code).
- **Reference aspects** per eval question (hand-written) to measure aspect coverage independently
  of the planner.
